问题解决（真实踩坑与处理）

  • 移动端点不动：手机浏览器对 pointerdown 触发不稳定 → 改用 touchstart 事件监听解决。
  • 音效不响：浏览器禁止自动播放音频 → 放进触摸事件的同步调用栈里播放并 resume AudioContext。
  • 无效交换不扣步：发现规则漏洞后修正为——只要进行了交换，无论是否消成都消耗 1 步。
  • 服务器常掉线：Python HTTP 服务在电脑睡眠/清理后会退出 → 固定用“启动游戏.bat”一键重启。
  • 公网分享失败：尝试过 serveo 等 SSH 隧道，断连频繁 → 退回局域网 IP 方案，保证同班同学能稳定访问。

标志性成果专题

三件作品：问题 · 用户 · 方案 · 复盘

🎮 梦梦消消乐

一个有账号、有关卡、有排行榜、在手机上也能玩的消除小游戏

❗ 问题

  • 初学者练手多是“看完就扔”的小 demo，我想做一个功能完整、真的有人玩的作品
  • 步数用尽直接弹“失败+自动重开”，体验很挫败
  • 想和同学比分数，但各玩各的没有共同排行榜
  • 早期本地服务器榜只在同一局域网共享，换网络/关机就断，朋友在外网看不到分数
  • 同学多用手机访问，电脑页面在手机上点不准、没声音

👥 用户

  • 我自己（验证想法、日常试玩）
  • 同班同学 / 朋友：手机浏览器随时打开，跨网络也能上同一张排行榜
  • 任何网络环境下的设备：家里、教室、用流量都能看到同一份云端榜单

💡 方案

  • 7×7 棋盘 + 7 种宠物，配置集中在 TYPES 数组，图案数量用 TYPES.length 动态读取
  • 账号密码 + localStorage 存档，进度跨刷新保留
  • 分档步数上限 + 提示/洗牌道具，控制难度曲线
  • 步数用尽改为萌宠安慰页（再来一次 / 登出换号），任何时候“重开”都可用
  • Supabase 云端排行榜：云数据库建 ranks 表，前端经 REST/RPC 调用数据库函数 submit_score 收分（同名玩家自动合并、保留最高分），任何网络的设备共享同一榜
  • 三级降级容错：云端 → Python 本地 /api/ranks → localStorage 缓存逐级回退，页面显示实时同步状态；云连不上也不影响游戏
  • 安全上只用可公开的 publishable 客户端密钥，写操作只能走数据库函数，service_role 主密钥不下发前端
  • touchstart 事件 + 同步调用栈播放音效，解决移动端问题

🪞 复盘

  • 做对的：先定硬约束再写代码（数据格式、步数规则、命名统一），后期少返工
  • 踩坑的：无效交换不扣步的漏洞、手机端事件差异、本地服务器/隧道易掉线
  • 升级：把排行榜从本地服务器迁到 Supabase 云数据库，第一次实践“前端直连云库 + RPC 函数 + 多级降级”
  • 学到的：真机测试不能省；“失败体验”也要设计；云服务要分清可公开密钥与主密钥；任何网络能力都要想好断了怎么办

🌈 心光谱 · 性向温柔测试与科普小屋

一个不贴标签、温柔讲科学的互动测评与科普网页

❗ 问题

  • 网上很多同类测试娱乐化、随便给人贴一个单一标签，甚至把取向“病理化”
  • 想自我了解的同学，缺少温柔、讲科学、中文且无评判的入口
  • 多数测试只给一个结果词，没有解释，更没有后续的科普和求助渠道
  • 话题敏感，使用者会担心隐私：做过的题不能被别人看到或上传

👥 用户

  • 想认真了解自己的青少年与同班同学
  • 对多元性别 / 光谱概念好奇、想找靠谱科普的读者
  • 正在自我认同中、需要温柔陪伴与求助资源的人

💡 方案

  • 24 道单选题，从性吸引、浪漫渴望、情感联结、性别在心动中的分量、吸引流动性等六个维度勾勒光谱，而非给单一标签
  • 结果页输出六维光谱 + 朋友式温柔解读，不评判、不定性
  • 30 种取向全图鉴；科普专区讲连续光谱、四种科学测量模型、易混概念与去病理化小史
  • FAQ 折叠问答 + 求助资源（含 24 小时危机干预热线 400-161-9995）
  • 约 72 KB 单文件、零外部依赖，纯前端运行、不收集任何数据，离线也能打开

🪞 复盘

  • 做对的：把“温柔、不贴标签”定为设计原则，贯穿题目、结果和科普全部文案
  • 做对的：不只做测试，还配科普与求助渠道，让作品有完整的价值闭环
  • 学到的：敏感话题的措辞要反复斟酌，科学内容要先查证再落笔
  • 学到的：“纯本地、不收集数据”本身就是安全感设计，单文件零依赖让任何人都能放心打开

🏃 跃动 · 运动技能自学计划

选一项运动，自动生成带计时跟练和打卡的从零自学计划

❗ 问题

  • 网上运动教程零散，初学者不知道从哪开始、按什么顺序练、每次练多久
  • 通用健身 App 给的是通用计划，不是“从零学会某一项运动”的专项路径
  • 自学容易跳过热身和拉伸导致受伤；没有阶段目标，练了也说不清进步在哪
  • 跟视频练要反复暂停看时间，手机上缺一个能边练边计时的小工具

👥 用户

  • 想利用课余碎片时间自学一项运动的同学（以手机使用为主）
  • 没有教练、不去健身房，打算跟着手机从零练的初学者
  • 我自己：需要计划、计时和打卡反馈才能坚持下来

💡 方案

  • 内置 16 个项目的动作数据库：每项 3 个阶段、基础+进阶各 5 个动作（含时长与要点），游泳再细分 4 种泳姿
  • 输入总天数和每日时长，算法按 热身 15% / 主训练 60% / 体能 15% / 拉伸 10% 自动排课，阶段内由基础到进阶渐进
  • SVG 环形计时器跟练：动作自动连播、上一个/下一个、进度点；主训练动作可一键搜索教学视频
  • 每日打卡、连续天数、进度环和三阶段结业里程碑（如“连续慢跑 30 分钟”“连续蛙泳 100 米”）
  • 完成打卡撒花 + 随机鼓励语；localStorage 离线保存；480px 手机优先并适配刘海屏安全区

🪞 复盘

  • 做对的：把“学什么（动作要点）”和“怎么练（计时+打卡）”合成一个闭环，不用在多个 App 间切换

最终学习复盘

能力变化 · 方法 · 失败 · 计划

📈 能力变化

  • 从只能照着例子改，到能把“我想要一个游戏/一个测试页”拆成功能点并做出来
  • 会用事件、localStorage、简单后端接口完成完整交互闭环
  • 开始有“用户体验”意识：失败也要安慰、手机也要能玩

🧭 方法

  • 小步迭代：先做能跑的最小版本，再按反馈一轮轮改
  • 把需求写成“硬约束”清单，避免边写边忘
  • 真机/真浏览器验证，不靠想象判断“应该能用”
  • 把踩过的坑记下来（如移动端事件差异），下次直接绕开

💥 失败与教训

  • 公网隧道方案在当前网络下频繁断连，前期投入浪费——选技术方案要先验证环境
  • 一次需求没说清楚，接入了不是自己想要的文件，发现后当天删除并换成正确的项目——沟通有歧义要当场澄清
  • 只在电脑上测试，导致手机端点击/音频问题很晚才暴露

🚀 下一步计划

  • 补齐阶段作业表与真实截图、手绘原型证据
  • 给作品集找一个长期可访问的托管地址（目前本地/临时链接不够稳定）
  • 继续学习响应式布局与一个前端框架，减少纯手写重复代码
  • 再做 1 个新项目，保持持续迭代而不是期末突击
